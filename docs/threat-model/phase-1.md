# Phase 1 threat model
Controls: forced PostgreSQL RLS with `app.tenant_id`; explicit permission checks; default-deny plugin capabilities; CSP/safe React rendering; no arbitrary plugin JS; mediated outbound HTTP for Wasm; redacted structured logging; request/execution limits; Wasm fuel/time/memory limits; signed-artifact verification fields; secure cookie/CSRF design for BFF sessions; non-root containers; CI dependency/container/secret scanning hooks; narrow CORS; problem+json errors. Threats considered include tenant bypass, confused deputy plugins, privilege escalation, forged workspace IDs, CSRF, XSS, SSRF, secret leakage, file access, event replay, duplicate delivery, malicious packages, migration tampering, supply-chain compromise, audit exposure, DoS, and insecure containers.

## Plugin supply-chain attack mitigations

Core out-of-box plugins such as Contacts are high-trust components and must be treated as release artifacts, not casual local code. The plugin manifest now carries `[supply_chain]` metadata for distribution type, source repository, source revision, provenance, artifact digest, signature, and SBOM. Core out-of-box plugins must provide the complete set so installers can verify origin, integrity, build identity, and dependency inventory before enablement.

Equivalent controls apply to any plugin according to distribution risk: reserved namespaces prevent impersonation of `platform.*` plugins; artifact digests pin installed versions; signatures and provenance attestations bind artifacts to reviewed source and CI; SBOM scanning detects vulnerable or prohibited dependencies; and upgrade reviews flag capability, permission, migration, outbound-network, secret, and event-publishing changes before rollout. See `docs/plugins/supply-chain.md` for the detailed control set.
